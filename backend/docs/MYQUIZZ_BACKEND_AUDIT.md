# Rà soát backend MyQuizz và kế hoạch sửa

Ngày rà soát: 2026-11-01. Mã backend: `/d/Coding/myquizz`, commit `1123ef3`. Đây là đánh giá mã nguồn và test cô lập; chưa kiểm thử xâm nhập trên môi trường triển khai hay đo tải thực tế. Ký hiệu **T** = tái hiện bằng harness giả lập; **M** = đường lỗi thấy trực tiếp trong mã, cần test tích hợp; **R** = rủi ro/việc cải thiện cần đo hoặc chốt chính sách. P0 là ảnh hưởng đến quyền/dữ liệu hoặc lỗi chặn luồng chính; P1 là lỗi chức năng/độ tin cậy; P2 là tối ưu và bảo trì.

## C. Thứ tự triển khai

1. **Đợt 1 — chặn lộ dữ liệu/quyền:** B01–B05, B35–B36. Làm test tái hiện trước, sau đó sửa và kiểm tra Android/frontend dùng DTO/token mới.
2. **Đợt 2 — phiên và tài khoản:** B06–B09, B26–B30, B32–B34, B37. Chốt chính sách thu hồi, thêm migration `jti`/family và concurrency tests.
3. **Đợt 3 — game đáng tin cậy:** B10–B20. Cần PostgreSQL/Redis test và nhiều socket giả lập; định nghĩa invariants cho seat, điểm, deadline, state và restart.
4. **Đợt 4 — dữ liệu quiz/upload:** B21–B25, B31, B38–B41. Transaction, schema và API error handling; giữ tương thích client.
5. **Đợt 5 — hiệu năng/vận hành:** C01–C18. Đo baseline trước khi tối ưu, báo cáo p50/p95, tải, CPU/RAM, số query và rủi ro còn lại.

Mỗi đợt tách thành PR nhỏ theo một lỗi/nhóm phụ thuộc, có test hồi quy và tài liệu API/socket khi contract đổi. Đợt 1–3 là phần mạnh nhất cho môn bảo mật; C06–C10, C15–C17 cùng số liệu trước/sau là phần mạnh nhất cho môn tối ưu.

## D. Bằng chứng và giới hạn

- 12 tình huống T đã tái hiện bằng harness TypeScript giả lập dependency (`MYQUIZZ_BACKEND_AUDIT_REPRO.cjs`), không phải exploit trên server thật. Kết quả ở `MYQUIZZ_BACKEND_AUDIT_REPRO_RESULTS.json`.
